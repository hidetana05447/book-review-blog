# 書評ブログへの記事追加

`secretary/website` にある個人ブログ「日常の視点を広げる書評ブログ」に、新しい書評記事を追加するための一連の作業をまとめたSkill。素のHTML/CSSサイトで、ビルドツールは使わない。

**このSkillを使う前に必ず`website/CLAUDE.md`を読むこと。** サイトのデザイン方針・記事フォーマット・コンテンツ制作フロー・SEOチェックリストなど、内容面のルールはすべてそこに書かれている。このSKILL.mdは「作業の手順と、過去につまずいたポイント」をまとめたものであり、内容ルールそのものを重複して書かない。両方を組み合わせて使うこと。

## 全体の流れ

1. Notionから読書メモを検索・取得する
2. 下書きを作成し、**本人の確認を得る**（確定させない）
3. 確認が取れたら、サムネイル画像を作る
4. 記事HTMLを作る
5. `index.html` / `sitemap.xml` / `website/CLAUDE.md`（書籍ラインナップ）を更新する
6. ブランチを切ってコミット・プッシュする（**mainへのマージ・公開は必ず本人の確認後**）

以下、各ステップの詳細と、過去に実際につまずいた注意点。

## ステップ1：Notionから読書メモを取得する

`website/CLAUDE.md`の「コンテンツ制作フロー」にある通り、Notionの「読書フォルダ」データベースが原本。Notion検索ツール（`notion-search`）で書名を検索し、該当ページを`notion-fetch`で取得する。

- 一番上に出てくるページだけでなく、検索結果に**関連する他のメモ**（同じ本について触れている別ノート、テーマ整理メモなど）が出てくることがある。メモが薄い場合や、もっと肉付けしたい場合は、それらも読んで材料にできないか検討する
- メモの中に「ガネーシャ」というAIキャラとのやり取りが含まれることがある。これはキャラクター・AIの発言として記事に出さない。ただし、そこで整理された概念・視点・解釈は、本人の言葉として地の文に落とし込んで使ってよい
- メモ内に勤務先名・同僚の実名・体調など個人情報にあたる固有名詞が出てきたら、**指摘を待たずに**下書きの時点で抽象化・伏せ字化を提案する（例：「オープンロジ」「松田さん」→「これまでの仕事」「事業視点を持つ先輩」）

## ステップ2：下書きを作成し、確認を得る

`website/CLAUDE.md`の「記事フォーマット」ルールに従って下書きを書く。ポイント：

- 対象書籍（書名＋著者）、ジャンルタグ、4〜8個程度の小見出し
- 前半で軽く「あらすじ・この本について」に触れ、著者名を地の文にも自然に入れる（構造化データの`author`情報と対応させるため）
- 気づき→日常への当てはめ、という流れを地の文に自然に組み込む
- 「なぜこの本を手に取ったか」は特別なエピソードがあるときだけ
- 末尾に「※本記事はNotionに書き溜めた読書メモをもとに、AIの編集サポートを受けて構成しています。」の注記

小見出しが8個を超えそうなボリュームになる場合は、無理に1本に収めず「嫌われる勇気」のように前編・後編に分割する（`website/CLAUDE.md`参照）。

**下書きの確認は、必ず本文全文（見出し＋本文の地の文まで書いたもの）を会話の中に直接貼って行う。** 見出しと要点だけの構成案（アウトライン）で先に方向性を合わせるのは任意だが、それは本文確認の代わりにはならない。構成案の合意だけで済ませて、そのままステップ3以降（ファイル作成・コミット）に進まないこと。本文全文の確認が取れてから初めて次に進む。修正依頼があれば反映してから再確認する。

**この確認は、ブラウザプレビューを見せることでは代替できない。** この環境のブラウザプレビュー機能は、ローカルファイルの相対パス（画像・CSS）を正しく読み込めないことがある（サンドボックスの制約で`localhost`接続がブロックされたり、`file://`表示が画像・CSSを読み込まない簡易スナップショットになったりする）。プレビューは補助的な見た目確認として使ってよいが、本文そのものの確認は必ずチャットのテキストで完結させる。

## ステップ3：サムネイル画像を作る

1. `assets/thumbnail-template.svg` をコピーし、`{{TITLE}}` `{{HOOK_LINE1}}` `{{HOOK_LINE2}}` `{{GENRE}}` を埋めて `images/thumbnails/<slug>.svg` として保存する
   - タイトルの文字数に応じたfont-sizeの目安はテンプレート内のコメントを参照
   - ジャンルタグは、既存記事の付け方（`小説`／`歴史・哲学`／`自己啓発`など、作品形式よりテーマ寄りの言葉）に揃える。迷ったら`reviews/`配下の既存ファイルを1つ`grep`して確認する
   - フックの一言は、記事のh1見出しをそのまま貼らず、要約・言い換えた短いキャッチコピーにする
2. `images/thumbnails/`ディレクトリで、同梱スクリプトを実行してOGP用PNGを生成する：
   ```bash
   cd images/thumbnails
   ../.claude/skills/add-book-review/scripts/make_og_png.sh <slug>
   ```
   （スクリプトの中身は`qlmanage -t -s 1200`でラスタライズ→`sips -c 630 1200`でセンタークロップ、という`website/CLAUDE.md`記載の手順そのもの）
3. 生成した`<slug>-og.png`を一度`Read`ツールで開いて、テキストが枠内に収まっているか目視確認する

## ステップ4：記事HTMLを作る

**単体書籍のレビューの場合**：`assets/review-template.html`をコピーし、`{{...}}`プレースホルダーを埋めて`reviews/<slug>.html`として保存する。構造化データは`Review`型。

**複数冊にまたがるテーマ記事の場合**：`Review`型は対象が1冊であることが前提なので使えない。代わりに`Article`型にして、対象書籍群を`about`配列（各要素が`@type: Book`、書名・著者）で紐づける。実例は`reviews/jinsei-no-kabe.html`や`reviews/asai-ryo-matome.html`を参照。関連する単体記事が別にある場合は、まとめ記事から個別記事へ、個別記事からまとめ記事へと相互リンクを張る（`嫌われる勇気`前編・後編、`朝井リョウ作品まとめ`の実例を参照）。

### 絶対に見落とさない注意点

- **`content="..."`属性値の中にストレートクォート(`"`)が入る場合は`&quot;`にエスケープする。** これを忘れると、その属性以降のHTMLが壊れる。テンプレートを埋めたあと、`grep -n 'content="[^"]*"[^ >]'`のようなパターンで見落としがないか確認する習慣をつけるとよい
- `<img>`タグには必ず内容の分かる`alt`属性を入れる（空にしない）
- `.review-meta`行に「公開日：YYYY年M月D日」を入れる
- ファイル名（slug）は既存記事の命名規則（ローマ字読み、ハイフン区切り）に揃える

## ステップ5：一覧ページ・サイトマップ・ラインナップの更新

1. **`index.html`**：
   - `<script type="application/ld+json">`内の`Blog`構造化データの`blogPost`配列に、新しい記事を`headline`/`url`/`datePublished`付きで追加する
   - `<ul class="review-list">`内にカードを追加する（サムネイル・ジャンル・タイトル・一言・alt属性・公開日）
   - **どちらも、公開日が新しい順になる正しい位置に挿入する。末尾に追加するだけで済ませない。** 同じ日付の記事が複数ある場合は、それらの中での順序は文脈に応じて判断してよい
2. **`sitemap.xml`**：新しい記事のURLを追記する
3. **`website/CLAUDE.md`の「書籍ラインナップ」**：該当書籍を「第一弾・未着手」から「公開済み」に移動する。複数冊テーマ記事の場合は、対象になった単体書籍が別々に「未着手」に残っていないかも確認する

## ステップ6：ブランチ・コミット・プッシュ

1. `git checkout -b add-review-<slug>`でブランチを切る（すでに未マージの関連ブランチがある場合は、その上に重ねて作ると後々のコンフリクトを避けやすい）
2. 変更したファイル一式を`git add`してコミットする
3. `git push -u origin add-review-<slug>`でプッシュする

**凛の作業はここまでで止める。mainブランチへのマージ・GitHub Pagesでの公開は、必ずヒデタナさん自身がGitHub上で行う**（`website/CLAUDE.md`の運用ルール）。ブランチをpushしたら、GitHubが表示するPR作成用リンク（`https://github.com/<owner>/<repo>/pull/new/<branch>`）を本人に共有して、作業を終える。

**注意（2026-08-17の教訓）**：このリポジトリの`main`にはブランチ保護がかかっておらず、`git merge` → `git push origin main`で直接pushすることが技術的には可能。かつて「クラウド上の自動タスクなら安全機構で拒否される」という前提を書いていたが、対話セッションでは実際に直接pushが成功することを確認済みで、その前提は誤りだった。つまりこのルールはGitHub側の技術的な強制力を持たない、**凛が自らこのルールを守ることに依存する取り決め**である。技術的に直接pushできてしまう状況でも、それを理由にマージ・公開を代行しないこと。

## よくあるつまずき（実例ベース）

- **ジャンルタグを既存の付け方と揃え忘れる**：作品形式（「小説」）とテーマ（「歴史・哲学」）が混在しているサイトなので、新規追加時にどちらに寄せるか本人に確認するか、既存の同ジャンル作品を参考にする
- **エスケープ漏れ**：上記参照。特に複数冊テーマ記事のdescriptionなど、長めの文章で見落としやすい
- **同じ内容を別のツール（Cursor等）で並行して作業していた場合のファイル名の食い違い**：ローマ字表記のブレ（例：`arujanon` vs `algernon`）で重複ファイルができることがある。作業前に`ls reviews/`と`ls images/thumbnails/`で同名・類似名のファイルがすでに存在しないか確認する
- **セクション数の目安を超える**：Notionのメモが濃い本だと8個を超えがち。無理に削るより前編・後編分割を検討する
- **サムネイルのフック文言が、意図せず単語落ちする**：h1タイトルを要約・言い換える際に、うっかり助詞や単語を欠落させたまま書いてしまうことがある（例：「わかっている側にいるだけでは」→「わかっている側だけでは」）。SVGを書いたら、h1と読み比べて意味が変わっていないか確認する
